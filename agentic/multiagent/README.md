# Мультиагентный онбординг Atlas

## Запуск для лекции

```bash
uv run python -m agentic.multiagent.demo --inject-invalid-args --inject-critic-error
```

Достаточно Ollama с установленной Qwen3 4B; локальный поиск не загружает embeddings.
Флаг `--inject-invalid-args` подменяет первый вызов оборудования на `order_id=-1`.
Валидация не выполняет функцию, возвращает ошибку модели и допускает одно исправление.
`--inject-critic-error` удаляет результат агента безопасности перед критикой.
Проверка полноты гарантированно обнаруживает отсутствие результата, повторно
исполняется только задача безопасности, затем критик запускается снова.
Успех генерации и исправления модели не гарантируется — лимиты завершают демо
явной ошибкой, а не выдуманным ответом.

Другие сценарии:

```bash
uv run python -m agentic.multiagent.demo
uv run python -m agentic.multiagent.demo --order-id 272
uv run python -m agentic.multiagent.demo --order-id 999
uv run python -m agentic.multiagent.demo --langfuse
```

`--order-id` является источником номера заказа. Если в свободном вопросе указан
другой номер, используется CLI-параметр. Демо предназначено для полной памятки
онбординга Atlas: план обязан включать все три роли, даже при коротком вопросе.
Произвольные проекты и задачи пока не поддерживаются.

## Архитектура и декомпозиция

```text
START
  planner (LLM -> валидированный план из трех задач)
  execute
    equipment (get_order -> get_delivery -> JSON)
    projects (поиск/чтение -> цитаты)
    security (поиск/чтение -> цитаты)
  critic (LLM + проверка полноты кодом)
    approved -> final -> END
    issues -> revise -> execute только указанные роли -> critic
```

Планировщик составляет вопросы подзадач самостоятельно. Граф ограничивает
допустимые роли, запрещает дубли и проверяет полноту плана. Исполнители получают
отдельные истории сообщений, инструкции и инструменты. Модель сама формирует
native tool calls, Python проверяет и исполняет функции.

| Роль | Инструменты | Ограничения |
| --- | --- | --- |
| equipment | `get_order`, `get_delivery` | отправление только из найденного заказа |
| projects | `search_knowledge_base`, `read_document` | категория `Projects`, 2026 |
| security | `search_knowledge_base`, `read_document` | категория `IT_Security`, 2026 |

Чтение разрешено только для документа, полученного поиском этой роли.
Произвольные пути и чтение вне каталога запрещены, симлинки пропускаются.

## Retrieval

По умолчанию `--retrieval local`: простой лексический поиск по словам с
фильтрами категории/года и top-3. Это RAG по тем же исходным markdown-документам,
но без векторного индекса. Он подходит для коротких учебных запросов с `Atlas`
и `ZTA-17`; не обеспечивает семантическую близость или качественный поиск синонимов.

Для настоящего векторного поиска по существующему индексу:

```bash
docker compose up -d qdrant
uv run python llamaindex/rag_llamaindex_demo.py index
uv run python -m agentic.multiagent.demo --retrieval qdrant
```

Этот режим лениво подключает LlamaIndex, `BAAI/bge-m3` и коллекцию
`robotex_docs_llamaindex`. Индекс автоматически не пересоздаётся.
Параметры окружения: `AGENTIC_QDRANT_URL`, `AGENTIC_COLLECTION`.
Адаптер проверен на Qdrant в памяти с подставными embeddings.
Сервер Qdrant и настоящая embedding-модель при разработке нового демо не запускались.

## Проверка результата

Контракты используют строгий Pydantic, лишние поля запрещены.
Каждая цитата должна дословно присутствовать в тексте, который инструмент
вернул именно этому агенту. Источники не подставляются автоматически.
При отсутствии данных агент возвращает `status=insufficient`, `evidence=[]`.
Критик проверяет покрытие задачи, но его смысловая оценка остаётся оценкой LLM.
Наличие дословной цитаты само по себе не доказывает полноту интерпретации вопроса.

Финальная памятка возвращается как JSON: `equipment`, `findings` и
`access_verified=false`. Сведения о проекте и требования доступа представлены
цитатами со ссылками `document_id` на файлы `data/knowledge_base/`.
Фактическая выдача доступов не проверяется. Финальный текст из памяти модели
не добавляется: ответ собирается из проверенных результатов исполнителей.

## Лимиты

- План и каждый структурированный ответ: один repair, максимум два запроса.
- Исследователь: максимум 5 запросов выбора инструментов, до 3 вызовов за шаг.
- Оборудование: максимум 5 запросов выбора инструментов, до 3 вызовов за шаг.
- Один repair инструментов на запуск каждого исполнителя.
- Один цикл адресного исправления после критика; после него критика обязательна.
- HTTP timeout по умолчанию 60 секунд на запрос, не общий лимит запуска.
- Ошибки сети завершают запуск; безусловных повторов сетевых запросов в коде нет.
- Неодобренный итог завершает программу с кодом 1; успех с кодом 0.

Параметры: `--model`, `--base-url`, `--timeout`, `--order-id`, `--retrieval`,
`--inject-invalid-args`, `--inject-critic-error`, `--langfuse`.
Модель/адрес можно задать через `AGENTIC_MODEL`, `AGENTIC_BASE_URL`.

## Trace

Вертикальный trace идёт в stderr, JSON — в stdout:

```bash
uv run python -m agentic.multiagent.demo --inject-invalid-args --inject-critic-error > onboarding.json 2> trace.log
```

Ключевые этапы: `PLAN_VALID`, `TASK_STARTED`, `TOOL_CALL`,
`REPAIR_REQUESTED`, `REPAIR_SUCCEEDED`, `TASK_COMPLETED`,
`CRITIC_RESULT`, `REVISION_REQUESTED`, повторный `CRITIC_RESULT`, `FINAL_VALID`.
События содержат роли и номера циклов; скрытые рассуждения модели не печатаются.

[Опциональный Langfuse и общие проверки](../README.md#langfuse).
