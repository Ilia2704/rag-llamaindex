# Tool calling и структурированный вывод

Минимальная демонстрация к лекции: локальная модель выбирает два инструмента,
приложение проверяет и выполняет вызовы, затем модель формирует проверяемый JSON.
Данные вымышленные и фиксированные, дата доставки не вычисляется от текущей даты.
Демо не требует Qdrant, embeddings, Docker, внешних API или ключей.

## Архитектура

Весь учебный код находится в `demo.py`:

1. `ChatOllama.bind_tools` передаёт модели определения функций с JSON Schema.
2. Модель возвращает `tool_calls` с именем и аргументами.
3. Реестр `TOOLS` разрешает только две заранее определённые функции.
4. Pydantic проверяет аргументы до выполнения. Затем приложение проверяет
   бизнес-правило: доставка должна принадлежать ранее найденному заказу.
5. Приложение выполняет функцию и проверяет результат отдельной Pydantic-схемой.
6. `ToolMessage` с соответствующим `tool_call_id` возвращает результат модели.
7. Когда необходимых фактов достаточно, отдельный вызов
   `with_structured_output(FinalAnswer.model_json_schema(), method="json_schema")` формирует JSON.
8. Финальная проверка сравнивает поля с результатами инструментов.

Модель выбирает вызовы самостоятельно. Приложение не подменяет их заранее
заданной последовательностью. Когда доказательств достаточно, цикл заканчивается
без дополнительного запроса на выбор инструментов. LangGraph для этого цикла не нужен.

## Инструменты и данные

| Функция | Вход | Выход |
| --- | --- | --- |
| `get_order` | положительный целочисленный `order_id` | наличие, статус, `shipment_id` |
| `get_delivery` | строка `shipment_id` вида `SHP-271` | наличие, статус, ожидаемая дата |

Заказ `271`: отправлен, отправление `SHP-271`, доставка `in_transit`, дата
`2026-10-15`. Заказ `272`: обрабатывается, отправления нет.
Остальные номера: заказ не найден. Для заказа без отправления второй вызов не нужен.
Оба инструмента только читают локальные демонстрационные данные.

## Валидация и ограничения

- Строгие типы, запрещённые дополнительные поля, ограничения ID и enum статусов.
- ISO-даты проверяются на JSON-границе через `model_validate_json`.
- Неизвестные функции не выполняются. Повтор успешной функции запрещён.
- Неверный `shipment_id` блокируется до выполнения инструмента.
- Одна попытка исправления ошибки инструментов на весь сценарий.
- Отдельно одна попытка исправления финального ответа.
- По умолчанию максимум 5 запросов выбора инструментов и до 2 запросов
  финального JSON. Таймаут 60 секунд на HTTP-запрос, а не на весь сценарий.
- Непарсируемые tool calls, сетевые ошибки и исчерпание лимитов завершают
  программу с кодом `1`. Успешное выполнение возвращает `0`.

Валидация не гарантирует правильного понимания произвольного вопроса моделью.
Демо проверяет структуру и согласованность ответа с выполненными вызовами.

## Запуск

Из корня репозитория, после `uv sync` и запуска локальной Ollama:

```bash
ollama pull hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M
uv run python -m agentic.toolcalling.demo
uv run python -m agentic.toolcalling.demo "Где мой заказ №272 и когда доставка?"
uv run python -m agentic.toolcalling.demo "Где мой заказ №999 и когда доставка?"
```

По умолчанию используется Qwen3 4B Q4_K_M с тем же именем, что и в основном
RAG-демо: `hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M`.
Точное имя установленной модели можно проверить через `ollama list`.
Для сравнения с меньшей моделью:

```bash
ollama pull qwen3:0.6b
uv run python -m agentic.toolcalling.demo --model qwen3:0.6b
```

Можно явно выбрать официальный тег Ollama:

```bash
ollama pull qwen3:4b
uv run python -m agentic.toolcalling.demo --model qwen3:4b
```

Поддержка native tool calling зависит от шаблона установленной модели;
официальный Ollama-тег предпочтителен. При реализации модели не запускались,
качество выбора инструментов и скорость на конкретном оборудовании не измерены.

Параметры: `--model`, `--base-url`, `--timeout`, `--max-steps` (1–10).
Переменные окружения: `TOOLCALLING_MODEL`, `TOOLCALLING_BASE_URL`.
CLI имеет приоритет. `.env` загружается автоматически.
Адрес по умолчанию: `http://localhost:11434`, без суффикса `/v1`.
Thinking отключён, temperature равна нулю.

## Показ repair loop

```bash
uv run python -m agentic.toolcalling.demo --inject-invalid-args
```

Учебный режим намеренно заменяет аргументы первого `get_order` на
`{"order_id": -1}` перед валидацией. Trace явно отмечает инъекцию.
Функция не исполняется, ошибка возвращается модели, которая получает одну
попытку исправления. Успех исправления зависит от модели.

## Вертикальный trace

Trace печатается в `stderr`, итоговый JSON — в `stdout`. Каждый этап имеет
порядковый номер и отдельный блок, аргументы и результаты печатаются с отступами:

```text
[04] TOOL_CALL
     {
       "name": "get_order",
       "arguments": {
         "order_id": 271
       }
     }
[05] ARGUMENTS_VALID
     {
       "order_id": 271
     }
[06] TOOL_EXECUTE
     "get_order"
...
[09] LLM_REQUEST
...
[18] STRUCTURED_OUTPUT_REQUEST
...
[19] FINAL_VALID
...
```

Номера иллюстративные. Trace показывает также `RESULT_VALID`,
`TOOL_RESULT_SENT`, `VALIDATION_ERROR`, `REPAIR_REQUESTED`,
`FINAL_VALIDATION_ERROR` и `FAILED`. Это последовательность действий приложения,
без вывода внутренних рассуждений модели.

Чтобы сохранить trace и JSON отдельно:

```bash
uv run python -m agentic.toolcalling.demo > answer.json 2> trace.log
```

## Проверки без модели

```bash
uv run python -m compileall -q agentic/toolcalling testing/test_toolcalling.py
uv run python -m unittest testing.test_toolcalling -v
```

Тесты используют подставные ответы LLM и не подключаются к Ollama.
Проверяются успешная цепочка, строгие аргументы, неизвестный заказ,
заказ без отправления, repair loop, запрет неизвестного инструмента,
бизнес-правило доставки, некорректный результат функции, отсутствие вызовов,
лимиты и исправление фактической ошибки финального JSON.

Финальный JSON возвращается как словарь и валидируется через
`FinalAnswer.model_validate_json`: корректные ISO-даты принимаются без
ослабления строгих типов. Trace показывает `FINAL_CANDIDATE` до проверки,
`REPAIR_REQUESTED` с ошибочными аргументами, `REPAIR_SUCCEEDED` с аргументами
до и после исправления. Для финального ответа аналогично выводятся
`FINAL_REPAIR_REQUESTED` и `FINAL_REPAIR_SUCCEEDED`.
